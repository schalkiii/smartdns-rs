# 2026-09-02

## Nightly builds startup_failure 修复

### 现象
Nightly builds workflow 连续 5 天（8/29~9/2）`conclusion=startup_failure`，"No jobs were run"。手动 workflow_dispatch 触发同样失败。`gh run view` 仅提示 "This run likely failed because of a workflow file issue"，无具体错误。

### 根因（reusable workflow 权限提升被拒）
- `nightly.yml`（caller）通过 `uses: ./.github/workflows/build.yml` 调用 reusable workflow。
- caller job 的 `permissions` 是被调用 workflow 的**权限天花板**：reusable workflow 只能降级、**不能提升**权限。
- nightly.yml caller 只声明了 `contents: read`，而 build.yml 的 build job 需要 `contents: write`（发布 release）→ 权限提升被 GitHub 拒绝 → startup_failure（无错误详情）。
- 参考：https://learnedgeek.com/Blog/Post/debugging-startup-failure-reusable-workflows（Bug #1: Reusable Workflows 不能提升权限）

### 修复（commit `a8ff30e`，已 push）
- `nightly.yml` caller job permissions 从 `{ contents: read, packages: write }` 改为 `{ contents: write, packages: write }`，与 build.yml workflow 级 permissions 完全对齐。
- 顺带给 nightly.yml 加了 `workflow_dispatch` 触发器（commit `e386944`），方便手动验证。

### 验证
- run 33608781110（head a8ff30e）：**12 个 jobs 正常启动**（11 in_progress + 1 queued），不再是 startup_failure。

### 经验（写入 MEMORY.md）
- **reusable workflow startup_failure 调试要点**：GitHub 不提供错误详情，需自行排查。最常见原因是 caller permissions 低于 reusable workflow 需求。caller 的 `permissions` 必须是 reusable workflow 所有 job permissions 的**超集**。
- **调试方法论**：startup_failure 无日志，只能用二分法——从最小配置逐步添加。
