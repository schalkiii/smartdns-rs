## 上游查询耗时过高问题调查

用户运行 smartdns 十余天，WebUI "上游查询耗时" 显示 700-800ms。

### 指标定义
- WebUI "上游查询耗时" = `cache_miss_avg_query_time_ms`（`src/app.rs` + `webui/.../page.tsx`），
  是**自进程启动以来的累计平均**（AtomicU64 求和/计数），重启后清零、具有粘性。
- 日志实测：prefetch 耗时 median=210ms / mean=222ms / p95=437ms；`resource too busy` 共 6030 次（占查询 ~32%），0 次超时。

### 根因（结合 hickory fork 源码 `crates/proto/src/xfer/dns_multiplexer.rs` 与 `resolver/src/name_server/name_server.rs`）
1. hickory `DnsMultiplexer::send_message` 在 `active_requests.len() > CHANNEL_BUFFER_SIZE(32)` 时返回 `ProtoErrorKind::Busy`。
2. busy 发生时，hickory `NameServerState::send` 的 `Err` 分支会 `set_status(Failed)`，
   导致**下一次查询强制重连**（触发 `connection_provider.rs` 的全局 `SOCKET_RATE_LIMITER` 200ms 串行化 + TLS 握手）
   → "busy → 重连 → 更慢 → 更多 busy" 恶性循环，直接推高延迟。
3. 旧逻辑（`src/dns_client.rs`）把 `Busy` 当作可重试错误，还**持有 per-NameServer 信号量槽位 sleep 50ms 重试**，加剧拥塞。

### 修复（已在 `src/dns_client.rs` 实施，cargo check 通过）
- 新增 `is_busy()`，将 `Busy` 从 `is_retryable()` 中剥离。
- busy 改为**快速失败**：立即返回错误，让 `NameServerGroup` 转向下一个上游，不重试、不占槽等待。
- 关键前提：当前 workspace 源码已有 `PER_NAMESERVER_CONCURRENCY=12` 信号量（<32），可从根本上抑制 busy；
  若运行中的二进制是早于该修复的旧版本（无信号量），需**从当前源码重新编译部署**才能彻底消除 busy。

### hickory fork `NameServerState::send` 让 Busy 不标记 Failed 的原理
- 现状（`resolver/src/name_server/name_server.rs:163-194`）：`send` 调用 `client.send(request).first_answer()`，
  无论成功/失败都走 `match response`；`Err` 分支**无条件** `self.set_status(Status::Failed)` + `record_connection_failure()`。
- 后果：busy（多路复用器瞬时过载）被当成"连接失败"，下一轮 `connected_mut_client()` 因 `status==Failed`
  强制走 `new_connection` 重连分支 → 触发 `connection_provider.rs` 全局 `SOCKET_RATE_LIMITER`（200ms 串行）
  + 协议握手（TLS 等），把一次本可瞬过（槽位释放后重试即可）的拥塞变成重连惩罚。
- 修复思路：在 `Err` 分支内，**若 `error.kind() == ProtoErrorKind::Busy` 则只返回错误、不置 Failed、不记连接失败**
  （也可顺带把 busy 计入延迟统计 SRTT 惩罚，但最关键是不触发重连）。这样 busy 只让本上游本轮跳过，
  由 smartdns 的 `NameServerGroup` 转向下游，本上游槽位稍后自然释放即可复用，切断"busy→重连→更慢"循环。
- 注意：需改动 git 依赖（rev `0.26.0-smartdns.5`，checkout 在 cargo git db），改后需 `cargo update`/重新拉取并重新编译 fork，工作量大于纯应用层修复；当前应用层修复已能缓解绝大多数场景，此项为可选深度优化。
